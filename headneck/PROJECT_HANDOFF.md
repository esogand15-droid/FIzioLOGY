## ۴. پروتکل عملی برای هر جلسه

۱. **شروع و تعیین محدوده:** دستور فعلی کاربر، شاخه و `git status`، محتوای پروژه، PDF موجود و گزارش‌های همان جلسه را بخوان. منبع/منابع، تعداد صفحات، hash، منابع مرجع و صفحات مورد انتظار را فهرست کن. کاری را که قبلاً انجام شده با ادعای تازه بازنویسی نکن.

۲. **ماتریس متن:** برای هر صفحهٔ منبع، متن استخراج‌شده، محل هر بند در رونویسی/موضوع و وضعیت مقابله را نگه دار. همهٔ متن‌ها، جدول‌ها، نکات و مطالب داخل تصویر را در نظر بگیر. استخراج فارسی و متن مخلوط RTL/LTR ممکن است جابه‌جا یا ناقص باشد؛ هر صفحهٔ منبع و اختلاف‌های مشکوک را با دیدن تصویر با وضوح مناسب کنترل و خطاهای رونویسی را اصلاح کن. سپس **مستقلاً اصل ↔ رونویسی ↔ خروجی** را بررسی کن؛ صرف تطابق JSON با خروجی اثبات درستی رونویسی نیست.

۳. **فهرست شکل‌ها:** تصاویر جزوه، نتر و گری مورد درخواست را با vision بررسی کن؛ هر شکل و **هر زیرشکل مستقل یک رکورد** با کتاب/فایل، شمارهٔ چاپی و PDF، عنوان، تشخیص ارتباط یا عدم ارتباط، دلیل انتخاب/رد، محل مقصد، مختصات برش و وضعیت وضوح/برچسب داشته باشد. در صفحات چندشکلی فقط یک رکورد کلی کافی نیست. شکل‌های مرتبط را نزدیک متن درست بگذار و قطع برچسب، خط راهنما، جزء مهم یا وضوح نامناسب را رفع کن. عدم بررسی همهٔ تصاویر را پنهان نکن.

۴. **محتوا و آموزش:** متن منبع را ثابت نگه دار؛ افزوده‌ها، جدول، شناسنامه، نکات و جهت‌یابی را به‌وضوح متمایز و مستند کن. اختلاف علمی یا تناقض منابع را بدون تغییر متن اصلی، در کادر مستقل، با ارجاع و بدون ادعای قطعیِ بی‌پشتوانه توضیح بده. منابع مرجع و تناسب متن و شکل را طبق دامنهٔ درخواستی کنترل کن.

۵. **ساخت و رفع نقص:** قبل از اصلاح موتور، کد مرتبط و رگرسیون جلسه‌های دیگر را بخوان. مشکلات فونت، اتصال فارسی/لاتین، پرانتز، شکست خطوط، سرعنوان جداافتاده، برش، جای شکل و فضای سفید را اصلاح کن. برای مسئلهٔ دشوار حداقل دو راهکار را مقایسه و نتیجه و دلیل انتخاب را ثبت کن؛ پس از آخرین تغییر دوباره بساز و آزمون کن.

۶. **بازبینی آخرین PDF:** hash دقیق فایل، آمار و همهٔ ارجاع‌ها را ثبت کن. **تک‌تک صفحات همان hash** را جداگانه با وضوح مناسب برای متن، تصویر، خوانایی، ریزبرچسب، حاشیه و شکست بررسی کن و برای هر صفحه شواهد و نتیجه ذخیره کن. thumbnail، رندر ماشینی، کنترل شمار تصویر یا صفحه به‌تنهایی مشاهدهٔ محتوایی نیست. پس از هر تغییر PDF شواهد hash قبلی را برای فایل جدید تأییدشده محسوب نکن.

۷. **QA مستقل و tracker:** نتایج و موارد مشخص را در گزارش پایدار با `NOT_STARTED`، `IN_PROGRESS`، `FAILED`، `FIXED` و `VERIFIED` ثبت کن. `FIXED` تا کنترل مجدد مستقل `VERIFIED` نیست. QA متن، تصاویر، صفحه‌آرایی، صحت فنی، علمی در دامنهٔ درخواستی، و رگرسیون جلسات قبلی را تفکیک کن؛ تعداد/هشدار/نقص، hash و مسیر شواهد باید دقیق باشند. توقف یا قطع کار را با tracker قابل‌ادامه ثبت کن.

۸. **انتشار:** در حالت عادی پس از انجام واقعی کنترل‌های خواسته‌شده، PDF و گزارش QA متناظر با همان hash را در مسیر پروژه بگذار، commit و push کن، دانلود از GitHub را با فایل محلی مقایسه کن و لینک بده. اگر کاربر صریحاً انتشار نسخهٔ موجود را بخواهد، محدودیت‌ها را دقیق بنویس و هرگز آن را کامل‌تأییدشده معرفی نکن. از افزودن نامزدهای بزرگ و فایل‌های scratch به Git بدون نیاز خودداری کن.

## ۵. دستورهای فنی کم‌خطر

از ریشهٔ مخزن اجرا کن. محیط مجازی ممکن است موجود نباشد:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
git status --short
```

برای جلوگیری از بازنویسی خروجی منتشرشده، ابتدا نامزد جدید را در مسیری تازه بساز؛ در مثال شمارهٔ جلسه را مطابق کار فعلی عوض کن. `--force` فایل موجود را بازنویسی می‌کند؛ فقط پس از بررسی و برای همان جلسه به کار ببر.

```bash
.venv/bin/python render/build_headneck.py --session hn04 --out /tmp/hn04_candidate.pdf
.venv/bin/python render/qa_headneck.py --session hn04 --pdf /tmp/hn04_candidate.pdf --report /tmp/hn04_candidate_qa.md
.venv/bin/python headneck/scripts/verify_pdf_integrity.py /tmp/hn04_candidate.pdf
sha256sum /tmp/hn04_candidate.pdf
git diff --check
```

**جلسهٔ ۳: flag اجباری برای نسخهٔ افزایشی فعلی.** بدون آن سازنده و QA محتوای پایهٔ قدیمی را می‌بینند. با این دستور فایل نامزد و گزارش آزمایشی بساز، نه اینکه بی‌اختیار PDF منتشرشده را بازنویسی کنی:

```bash
HUMSYAR_HN03_WIP=1 .venv/bin/python render/build_headneck.py --session hn03 --out /tmp/hn03_candidate.pdf
HUMSYAR_HN03_WIP=1 .venv/bin/python render/qa_headneck.py --session hn03 --pdf /tmp/hn03_candidate.pdf --report /tmp/hn03_candidate_qa.md
.venv/bin/python headneck/scripts/verify_pdf_integrity.py /tmp/hn03_candidate.pdf
.venv/bin/python headneck/scripts/check_hn03_transcription_integration.py
.venv/bin/python headneck/scripts/check_hn03_update_wip.py
```

نامزد تازه ممکن است از نظر metadata/hash با PDF قبلی فرق داشته باشد؛ خروجی خود را دوباره QA و صفحه‌به‌صفحه بررسی کن. ابزارهای `hn03_audit_evidence.py`، `hn03_image_output_manifest.py` و `verify_pdf_integrity.py` برای آرگومان مسیر طراحی شده‌اند؛ از اجرای `--help` به‌عنوان تست بدون بررسی کد خودداری کن. دستورات اختیاری آماده‌سازی محتوا را بدون خواندن اثرشان اجرا نکن.

نکات فنی شناخته‌شده: در استخراج PDF، ترتیب دوزبانه، علائم و حروف فارسی می‌تواند نادرست باشد؛ متن استخراجی گری در بخش‌هایی به‌دلیل نگاشت فونت مخدوش است. برای رندر/استخراج می‌توان از PyMuPDF و Pillow در محیط وابستگی‌ها استفاده کرد؛ نصب `pdftotext` یا `tesseract` را مفروض نگیر. تصاویر PDF و نام فونت subset را صرفاً با شمارش ساده یا `getBestCmap()` قضاوت نکن. `.gitattributes`، فایل‌های `pdf/*.pdf` را باینری نگه می‌دارد؛ سلامت فایل و تطابق بایتی دانلودشده از GitHub را کنترل کن.

## ۶. شیوهٔ کار با Git و تحویل

- در گفت‌وگوی جدید **شاخهٔ فعال اعلام‌شده توسط محیط** و وضعیت آن را بررسی کن؛ روی همان شاخه کار و فقط طبق دستور محیط push کن. شاخه یا commit قدیمی را بدون بررسی جاری فرض نکن و شاخهٔ دیگری نساز.
- فقط فایل‌های مربوط به کار را stage کن؛ تغییرات کاربر و فایل‌های ناتمام موجود را حذف یا بازنویسی نکن. گزارش را مطابق SHA همان PDF بنویس.
- پس از انتشار، لینک مستقیم دانلود PDF و لینک گزارش QA/commit را ارائه کن و به‌اختصار مشخص کن چه مواردی تأیید شده و اگر کاربر انتشار ناقص را صریحاً خواست چه مواردی هنوز کامل نشده‌اند.
- این فایل را همراه با tracker جلسه و وضعیت فایل‌های منتشرشده بعد از هر تحویل به‌روز کن، به‌خصوص وقتی منبع جلسهٔ ۷ پیدا شد یا hash نسخه‌ای تغییر کرد.
